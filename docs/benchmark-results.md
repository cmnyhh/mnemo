# LoCoMo 评测结果（mnemo 1.3.0）

## 环境

| 项 | 值 |
| --- | --- |
| 机器 | 2 核 / 3.9G，Arch Linux |
| 服务 | mnemo 1.3.0，容器内 8080，宿主 127.0.0.1:8090 |
| 向量库 | Qdrant 1.12.4 |
| 数据库 | PostgreSQL 18 + pg_textsearch（BM25） |
| embedding | `Qwen/Qwen3-Embedding-4B`，2560 维（SiliconFlow） |
| 精排 | `Qwen/Qwen3-Reranker-0.6B` |
| 作答 / 判分 | `deepseek-v4.1-flash`（`model.huhufox.love` 自建端点） |
| 检索参数 | hybrid，topK=12，注入预算 8000 字，`dense-min-score` 0.30，`abstain-threshold` 0.10 |

## 协议

数据集是 [LoCoMo](https://github.com/snap-research/locomo) 的 `locomo10.json`：10 段跨月对话、
272 个会话、5882 轮、1986 道题，全部题目都跑，不抽样。

- **每段对话一个独立租户**。通行做法，也是唯一能避免跨对话串味的方式——所有 10 段放在同一个库里，
  问 A 段的问题会被 B 段的记忆挤掉 top-k。
- **入库粒度**：主结果按**逐轮**写入，5882 条，每条一轮对话（产品插件真实的写入粒度）。
  另有一组「整段会话一条」的对照，见后文。
- **检索**：题目原文直接作为 query，取服务返回的 `injection`（产品真实注入块），不额外拼提示词。
- **作答**：把注入块给模型，要求只回短语，检索不到就回 `NOT MENTIONED`。
- **判分**：另起一次调用，给定题目、标准答案、作答，只回 CORRECT / WRONG。判分器先用
  已知对/错配对校准过（10/10 自洽、0/10 误放行）。
- **adversarial 类**（446 题）的题目预设了一件从未发生的事，标准答案字段里只有陷阱答案，
  所以拒答记对、顺着答记错。

三个指标分开报：召回不需要大模型，客观；准确率会掺进作答模型的水平。

## 主结果：逐轮入库

| 类别 | 题数 | 证据召回(任意) | 证据召回(全部) | 准确率 | 检索 p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 multi-hop | 282 | 64.5% | 13.5% | 18.8% | 298 ms |
| 2 temporal | 321 | 66.0% | 59.5% | 43.9% | 299 ms |
| 3 open-domain | 92 | 45.7% | 25.0% | 20.8% | 302 ms |
| 4 single-hop | 841 | 71.1% | 68.6% | 56.1% | 303 ms |
| 5 adversarial | 446 | 61.9% | 60.5% | 83.4% | 302 ms |
| **合计** | **1982** | **66.1%** | **55.4%** | **53.3%** | **301 ms** |

1986 道题里有 4 道本身没有标注证据（open-domain 的常识题），不参与召回统计。

## 对照：整段会话当一条记忆

同一套系统、同一批题，只把入库粒度改成「一个会话一条」（272 条）：

| 类别 | 题数 | 证据召回(任意) | 证据召回(全部) | 准确率 | 检索 p50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 multi-hop | 282 | 98.6% | 63.5% | 12.4% | 171 ms |
| 2 temporal | 321 | 95.6% | 93.8% | 6.2% | 179 ms |
| 3 open-domain | 92 | 78.3% | 58.7% | 2.1% | 168 ms |
| 4 single-hop | 841 | 99.2% | 99.0% | 8.4% | 162 ms |
| 5 adversarial | 446 | 98.9% | 98.9% | 94.2% | 160 ms |
| **合计** | **1982** | **97.5%** | **91.2%** | **27.6%** | **165 ms** |

两张表放在一起看，是这次评测最值得记的一件事：

**召回 97.5%、准确率 27.6%**——证据明明都召回了，模型却答不出来。原因是注入块对每条记忆
最多渲染 220 字（`Ranking.java:281`），整段会话被截断成残句，答案多半落在截断之后。
反过来，逐轮入库召回只有 66.1%，准确率却有 53.3%：给到模型的是**能读完的完整句子**。

结论不是「召回率没用」，而是：**召回率必须和「召回到的东西能不能被用」一起看**。
220 字的上限对「一条记忆 = 一个事实」是够的，对整段对话不够——产品的写入粒度本来就是前者。

## 观察

1. **多跳最弱**（18.8%）。证据全部命中的比例只有 13.5%：多跳题需要两条以上证据同时进 top-12，
   而 top-12 只是每段约 588 条记忆的 2%。
2. **adversarial 的分数会被过度弃权抬高**。粗粒度那组里 94.2% 的「正确」几乎全是拒答——
   上下文全是长文、找不到答案，模型自然说不知道。所以这一类必须和 single-hop 并排看，
   不看 single-hop 的 94.2% 是假象（同一组 single-hop 只有 8.4%）。
3. **精排会被供应商限流打回**。并发 6 检索时 1986 次里有 1543 次精排失败（78%），
   报 `HTTP 429 TPM limit reached`，服务自动退回 RRF 排序并照常返回结果。
   降级有指标可查：`mnemo_degrade_total{kind="rerank"}`。这是这次评测顺带暴露的运维事实——
   精排是外部 API，配额不够时会静默降级，而结果仍然看似正常。
4. **调大 topK 没用，真正的上限是 `rerank.top-n`**。把 topK 从 12 提到 30 重跑一遍，
   召回只从 66.1% 变成 66.6%。原因是 `SearchService:181` 只把融合后的前 `rerank.top-n`（=12 条）
   送去精排，而精排生效时没被精排过的条目会被丢弃——所以输出条数不可能超过 12。
   想真正加深召回，要同时调大 `rerank.top-n`，单独调 topK 是空转。

## 1.3.1：注入块的两处改动与实测效果

### 改了什么

1. **单条记忆的上限从写死 220 字改成按预算自适应**（预算的 12%，下限 220、上限 900）。
   预算 8000 时单条 900 字，一轮对话（190~400 字）整条进得来。
   老实现无论预算多大都只给 220 字，剩下的预算全空着。
2. **长记忆不再从头上硬砍**：保头部（时间戳 / 说话人），再从「和 query 有词面交集」的那句
   往后取，全程按句边界切。老实现砍到 220 字时，答案常常正好在被砍掉的后半句。
3. **精排窗口跟随 topK**（`max(rerank.top-n, topK)`，上限 64）。窗口原先固定 12，
   而精排生效时只回精排过的条目 —— 所以调大 topK 一直是空转（观察第 4 条）。

### 结果（同一批题、同一作答/判分模型）

| 版本 | 检索设置 | 召回(任意) | 召回(全部) | 准确率 |
| --- | --- | ---: | ---: | ---: |
| 1.3.0 | topK=12 | 66.1% | 55.4% | 53.3% |
| 1.3.1 | topK=30 | 65.2% | 54.7% | **55.7%** |

召回没变（差 0.9 点在噪声内），准确率 **+2.5 点**。分项：single-hop +5.0、multi-hop +3.2、
open +2.1、temporal −0.6、adversarial −0.4。

结论：**同样的证据，注入得更完整，模型就能多用出 2.5 个点**——和上一节估的
「截断损失约 2.8 点」对得上。single-hop 涨得最多，正是因为那类题的答案常落在长轮次的后半句。

### 一次负优化（已回退）

顺手试了「两路候选池从 40 加深到 100」（topK=50）：召回从 66.1% **掉到 43.3%**，
multi-hop 从 64.5% 掉到 45.4%。

原因是 RRF 只看名次不看分数。候选池变大后，真正证据的名次更深、RRF 分被摊薄，
而精排窗口只取融合后的前 50 条 —— 深层证据进不了窗口，窗口内反而塞进更多低质候选。
**检索深度不是越大越好**：40 是这套「RRF + 精排 + 剪枝」组合的合适位置，配置已回退。

## 与 MemOS 的口径差异

MemOS 在 README 上挂的 LoCoMo 是 **88.83**（单一数字），但没有公开作答模型、判分模型和检索深度。
本报告的数字是：自建端点 `deepseek-v4.1-flash` 作答并判分、topK=12、注入预算 8000 字、逐轮入库。

**两个数字不能直接比高低**：换一个更强的作答模型，准确率会整体上移；把 `rerank.top-n` 从 12 提到 30
并同步调大 topK，召回也会变（单独调 topK 不会，见观察第 4 条）。想做同条件对比，得把 MemOS 用同一份题、
同一个作答模型、同一个判分器跑一遍——那是另一件事，本报告没有做。

可比的只有召回率：它不依赖任何大模型，是检索能力的硬指标，也是可以逐条复算的。

## 复现

```bash
python3 bench/locomo/run.py ingest --base http://127.0.0.1:8090 --data locomo10.json \
    --granularity turn --concurrency 8          # 5882 条，逐轮
python3 bench/locomo/run.py ask    --base http://127.0.0.1:8090 --data locomo10.json --topk 12
python3 bench/locomo/run.py judge  --model deepseek-v4.1-flash
python3 bench/locomo/run.py report
```

`ingest` 按 `idempotencyKey` 去重，`ask` / `judge` 按题号跳过已完成的；三段都可中断重跑。
原始结果（逐题检索、逐题判分）留在服务器 `bench/locomo/out/` 下，可按类别、按对话复算。

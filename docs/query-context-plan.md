# 检索层查询构造：从「用户原话」到「可检索的查询」

> **状态：L1 已实施并被实测否决（1.5.0~1.5.2），1.5.3 移除；L0 仍待做。**
> 本文保留完整实验记录，作为「不再做查询改写」的依据。
> 相关但结论不同的记录：[`query-rewrite.md`](query-rewrite.md)（无条件改写已证伪）。

## 1. 现状：输入原样进检索，不带任何上下文

`plugin/src/index.ts` 的 `queryText()` 把本步骤所有 `source.kind === 'user'` 的文本块用换行
拼起来，原样交给 `POST /v1/memory/search`，中间没有任何加工：

```ts
for (const message of messages) {
  if (message.source.kind !== 'user') continue
  const text = textOf(message.content)
  if (text.length > 0) parts.push(text)
}
return parts.length === 0 ? undefined : parts.join('\n')
```

后果是：`那这个呢`、`继续`、`改成 14 天` 这类输入，检索词就是这几个字。BM25 抓不到实体，
向量也缺少可区分的方向——不是排序不准，是**查询本身携带的信息量太低**。

## 2. 与 10-22 已证伪方案的区别

`query-rewrite.md` 那次做的是「无条件扩展 + 替换原查询」，LoCoMo 1986 题：
召回 65.3% → 57.6%（−7.7pt）。它的结论必须保留：**不要无条件改写**。

但它的边界也要看清：评测集的问句本身完整自足（"When did Caroline go to the LGBTQ
support group?"），缺的是**词汇层**（问句说 destress，记忆里写 pottery class），
不是上下文。真实对话里常见的失败是反过来的：句子短到没有实体，缺的是**上下文**。

| | 10-22 的方案 | 本待办 |
|---|---|---|
| 触发 | 每轮无条件 | 仅当 query 过短或含指代 |
| 作用 | 替换原查询 | 原结果保底，提炼后再补一次检索 |
| 失败后果 | 整体 −7.7pt | 最多补进几条噪声，主路径不变 |
| 针对 | 词汇错配 | 上下文缺失 |

**「再检索一次」而不是「替换」是这个提法里最关键的一点**：并集不会让原本能命中的东西
消失，而替换会。上一轮退化的根源正是替换。

## 3. 实测：决定弃权的是措辞，不是长度（2026-10-27，线上 1.4.9）

同一个事实（"每天凌晨 3 点备份 PostgreSQL"），换十种问法打 `/admin/api/recall`：

| query | 字数 | 弃权 | 命中 | 最佳精排分 |
| --- | ---: | :---: | ---: | ---: |
| `备份` | 2 | 否 | 6 | 0.881 |
| `备份文件` | 4 | 否 | 6 | 0.876 |
| `数据库备份` | 5 | 否 | 5 | 0.792 |
| `备份目录` | 4 | 否 | 5 | 0.767 |
| `数据库 备份 目录` | 8 | 否 | 4 | 0.742 |
| `备份 目录` | 5 | 否 | 6 | 0.705 |
| `备份放在哪里` | 6 | 否 | 4 | 0.665 |
| `备份文件放在哪里` | 8 | **是** | 0 | — |
| `备份文件 目录` | 6 | **是** | 0 | — |
| `数据库备份文件放在哪个目录` | 13 | **是** | 0 | — |

长输入三组：

| 输入 | 结果 |
| --- | --- |
| README 片段 1200 字（整段都在讲 mnemo） | 7 命中，top 0.844，444 ms，未降级 |
| 同一段 1500 字 + 末尾「我只想知道备份文件放哪个目录」 | 7 命中，但备份那条排第 2（0.792） |
| **无关背景** 851 字（跑鞋）+ 同一个问题 | **弃权** |
| 只有那一句问题（28 字） | **弃权** |

两个结论：

1. **没有任何切分或改写**：`Tokenizer` 无上限，中文按 bigram 滑窗切完直接 `join(" ")`
   进 BM25；`embed(query)` 整段进向量。1200 字照收，不报错，延迟只多约 50 ms。
2. **破线的是"记忆里不存在的限定词"，不是长度**。`备份` 与 `备份文件` 都在 0.87 上下，
   可一旦加上"放在哪里""哪个目录"，分数就掉到 0.10 以下——因为被检索的那条记录里
   没有"目录"这个信息，cross-encoder 对 query 中无法被 passage 满足的限定词逐个扣分，
   攒够几个就弃权。长短本身几乎不参与。

这条实测推翻了"扩展"的方向：**该做的是减词，不是加词**。而它不与
`query-rewrite.md` 矛盾——那次证伪看的是**中位名次**（113→120，去掉壳不改善排序），
这里看的是**阈值通过率**（去掉壳能把 0 条救回 5~6 条）。同一个动作，两个指标。

## 4. 三层，按成本递增

### L0 · 上下文拼接（先做，零延迟零成本）

query = 最近 1~2 条用户输入 + 上一轮回复的**尾部**若干字。

为什么不只加用户输入：`那这个呢` 加上前一句 `那这个呢` 依然没有实体，真正的主题在
上一轮回复里。为什么取尾部：结论、文件名、参数值通常落在最后；这与 1.4.x 里 `clip()`
「头尾各留一半」是同一条经验。

实现位置待定：`agent/pre-step` 的 `messages` 是 `UserMessage[]`、只覆盖当前 step，
拿不到历史 assistant 文本。两条路——
1. 插件端缓存最近一轮的回复（复用 `session/event`），拼进 query；
2. 把 `sessionId` 一并传给服务端，由服务端按会话补最近 N 轮（服务端已有 episode 记录，
   但要确认轮次边界与跨会话污染）。

倾向 1：改动在插件内，不新增服务端语义。

### L1 · 条件触发重试（1.5.0~1.5.2 实施，1.5.3 移除）

§3 的实测把这个动作从「补全」改成了「压缩」：把 query 压成名词短语后再检索一次。
1.5.0 做规则版，1.5.1 补模型版，用 `search.squeeze-retry` 选档：

| 取值 | 做法 | 代价 | 弱点 |
|---|---|---|---|
| `off` | 不动 | 0 | — |
| `rules` | 删疑问/套话（`QuerySqueeze`） | 0 ms | 只认枚举过的形状，跨不了词汇 |
| `llm` | 看着落选候选改写（`LlmQueryDistiller`） | 一次模型调用 | 多一次外部依赖 |
| `both` | 先规则，没救回来再上模型 | 同上 | — |
| `always` | 每轮都用规则查询两路召回 | 每轮多一次嵌入 | 只是「提前做」，不改召回上限 |

三者的共同前提：**只在弃权后触发**，且原结果保底（并集，不是替换）。

规则版的硬伤是泛化性——它假定了用户问法落在枚举过的形状里；而真正难的一步是
**词汇不对齐**（用户说「备份」，库里写「pg_dump 导出」），规则一个词都补不上。
模型版为此把**落选候选**一起喂进去（伪相关反馈）：让它看着候选原文挑词，而不是凭空猜。
只给问题不给候选时，模型只能用问题自己的词重写一遍，和规则去噪没有本质区别。

模型选择有硬约束（见 `query-rewrite.md` §1）：**不能用推理模型**，p50 2.6s，
检索路径本身 p50 只有 293 ms；小模型 436~452 ms 是可用上限。

**结论（§8）：三档 Hit@3 完全一致，改动无效。** 1.5.3 已删除 `QuerySqueeze`、
`LlmQueryDistiller` 与 `search.squeeze-retry` 配置项，检索恢复为「用户原话直查 +
模型主动调工具」两条路。此表仅作历史记录，不再有对应代码。

### L2 · 无条件改写（不做）

已被端到端证伪，不再尝试。

## 5. 验收方式

不用 LoCoMo：它的问句分布与真实对话相反，看不出这个改动的收益。

自造用例也不行——§3 那十条问法是照着规则表写出来的，用它评估规则版等于自己考自己。
改为**从库里随机抽真实记忆，让模型反推「用户会怎么问」**，并把问法分两档：

| 档位 | 生成要求 | 考的是 |
|---|---|---|
| `literal` | 正常提问，允许复用原文词汇 | 现实中的多数情况 |
| `paraphrase` | 禁止出现原文名词，必须换说法 | 词汇不对齐时的压力测试 |

判据：弃权率（主）、Hit@1/3/5（源记忆的名次）、延迟。样本 24 条 × 2 档 × 3 策略。
当时的脚本 `scripts/eval-retry.py` 直接切 `search.squeeze-retry` 做对照，随功能一并移除；
结论已固化在 §8，重跑无意义。

**采样必须过滤 `status=active`**：第一版没过滤，24 条里混进了已软删的记录（都是早期探针
留下的），于是「目标条目排第几」这一栏结构性为空——删除的条目检索路径本来就不返回。
那一版得出的「重试救回来 0 条有效」因此作废，不能用。

## 6. 风险

- 拼接引入上一轮的噪声实体，把检索带到无关方向（L0 的主要风险，靠长度上限约束）；
- 检索路径的延迟预算很紧：p50 293 ms，任何加在它前面的模型调用都要按「首字延迟」计价，
  这也是模型版最终没有留下的原因之一；
- 会话隔离：补全时绝不能跨租户取上下文。

## 7. 建议顺序

只做 L0。L1 已证伪并移除（§8），L2 不做。

## 8. 对照结果（2026-10-27，线上 1.5.2，24 条 active 记忆 × 2 档问法）

| 策略 | 问法 | 弃权率 | Hit@1 | Hit@3 | Hit@5 | 延迟 |
|---|---|---|---|---|---|---|
| `off` | literal | 0.0% | 17.4% | 56.5% | 69.6% | 319 ms |
| `off` | paraphrase | 4.2% | 33.3% | 54.2% | 58.3% | 312 ms |
| `rules` | literal | 0.0% | 17.4% | 56.5% | 69.6% | 347 ms |
| `rules` | paraphrase | 0.0% | 33.3% | 54.2% | 58.3% | 310 ms |
| `llm` | literal | 0.0% | 21.7% | 56.5% | 69.6% | 317 ms |
| `llm` | paraphrase | 0.0% | 33.3% | 54.2% | 58.3% | 666 ms |

三条结论，都跟预期相反：

1. **弃权本身很罕见**（全样本 1/47）。第一版评测里 16.7% 的弃权率是样本错误的产物——
   那 24 条里有已软删的记录，什么都搜不到，自然弃权。弃权在多数时候意味着
   **库里没有这条信息**，不是「词不好」；而前者任何改写都救不了。
2. **改写没有提升准确率**。Hit@3 在三种策略下完全一致（56.5% / 54.2%），
   唯一被救回来的那条也没有进前三。`llm` 在 literal 上多出的 1 条 Hit@1 属噪声
   （该档弃权率为 0，这条路径根本没触发）。
3. **词汇不对齐的影响比想象小**。`paraphrase`（禁用原文名词）的 Hit@3 只比 `literal`
   低 2.3pt，说明向量 + 精排本来就吃得下同义改写；§3 观察到的「备份文件放在哪里」弃权
   属于另一类问题——**问句加了条目里没有的限定词**，不是同义词错配。

因此 `search.squeeze-retry` 默认改为 `off`，随后整体移除：证据不支持它存在。
当时的取舍是「保留 rules（零成本）与 llm（实验档）」，最终判断是**留着也没人开**——
模型版在旧提示词下还会把候选里的具体值抄进查询（把别人的密码当成答案，0.898 分），
收紧成「候选不相关时禁用其具体值」后现象消失，但代价 +350 ms，收益为零。

**真正该先做的仍是 L0**：短指代查询（「那这个呢」）缺的是上文实体，
压缩和改写都无中生有不了。这一点被这轮数据佐证：改写只在「问题本身有实体、
但措辞加了限定词」时才有意义，而这恰是少数。

真正的兜底是**模型主动调 `memory_search`**：它看得见上下文，能自己把「那这个呢」
补成完整问句再查，比服务端猜词可靠。自动注入这一层因此回归为纯检索，不做加工。

# 检索层查询构造：从「用户原话」到「可检索的查询」

> **状态：未实施（TODO）。** 这份文档记的是判断与实验设计，不是已定方案。
> 相关但结论不同的记录：[`query-rewrite.md`](query-rewrite.md)（无条件改写已证伪）。

## 1. 现状：输入原样进检索，不带任何上下文

`plugin/src/index.ts` 的 `queryText()` 把本步骤所有 `source.kind === 'user'` 的文本块用换行
拼起来，原样交给 `POST /v1/memory/search`，中间没有任何加工：

```ts
for (const message of messages) {
  if (message.source.kind !== 'user') continue
  const text = textOf(message.content)
  if (text.length > 0) parts.push(text)
}
return parts.length === 0 ? undefined : parts.join('\n')
```

后果是：`那这个呢`、`继续`、`改成 14 天` 这类输入，检索词就是这几个字。BM25 抓不到实体，
向量也缺少可区分的方向——不是排序不准，是**查询本身携带的信息量太低**。

## 2. 与 10-22 已证伪方案的区别

`query-rewrite.md` 那次做的是「无条件扩展 + 替换原查询」，LoCoMo 1986 题：
召回 65.3% → 57.6%（−7.7pt）。它的结论必须保留：**不要无条件改写**。

但它的边界也要看清：评测集的问句本身完整自足（"When did Caroline go to the LGBTQ
support group?"），缺的是**词汇层**（问句说 destress，记忆里写 pottery class），
不是上下文。真实对话里常见的失败是反过来的：句子短到没有实体，缺的是**上下文**。

| | 10-22 的方案 | 本待办 |
|---|---|---|
| 触发 | 每轮无条件 | 仅当 query 过短或含指代 |
| 作用 | 替换原查询 | 原结果保底，提炼后再补一次检索 |
| 失败后果 | 整体 −7.7pt | 最多补进几条噪声，主路径不变 |
| 针对 | 词汇错配 | 上下文缺失 |

**「再检索一次」而不是「替换」是这个提法里最关键的一点**：并集不会让原本能命中的东西
消失，而替换会。上一轮退化的根源正是替换。

## 3. 实测：决定弃权的是措辞，不是长度（2026-10-27，线上 1.4.9）

同一个事实（"每天凌晨 3 点备份 PostgreSQL"），换十种问法打 `/admin/api/recall`：

| query | 字数 | 弃权 | 命中 | 最佳精排分 |
| --- | ---: | :---: | ---: | ---: |
| `备份` | 2 | 否 | 6 | 0.881 |
| `备份文件` | 4 | 否 | 6 | 0.876 |
| `数据库备份` | 5 | 否 | 5 | 0.792 |
| `备份目录` | 4 | 否 | 5 | 0.767 |
| `数据库 备份 目录` | 8 | 否 | 4 | 0.742 |
| `备份 目录` | 5 | 否 | 6 | 0.705 |
| `备份放在哪里` | 6 | 否 | 4 | 0.665 |
| `备份文件放在哪里` | 8 | **是** | 0 | — |
| `备份文件 目录` | 6 | **是** | 0 | — |
| `数据库备份文件放在哪个目录` | 13 | **是** | 0 | — |

长输入三组：

| 输入 | 结果 |
| --- | --- |
| README 片段 1200 字（整段都在讲 mnemo） | 7 命中，top 0.844，444 ms，未降级 |
| 同一段 1500 字 + 末尾「我只想知道备份文件放哪个目录」 | 7 命中，但备份那条排第 2（0.792） |
| **无关背景** 851 字（跑鞋）+ 同一个问题 | **弃权** |
| 只有那一句问题（28 字） | **弃权** |

两个结论：

1. **没有任何切分或改写**：`Tokenizer` 无上限，中文按 bigram 滑窗切完直接 `join(" ")`
   进 BM25；`embed(query)` 整段进向量。1200 字照收，不报错，延迟只多约 50 ms。
2. **破线的是"记忆里不存在的限定词"，不是长度**。`备份` 与 `备份文件` 都在 0.87 上下，
   可一旦加上"放在哪里""哪个目录"，分数就掉到 0.10 以下——因为被检索的那条记录里
   没有"目录"这个信息，cross-encoder 对 query 中无法被 passage 满足的限定词逐个扣分，
   攒够几个就弃权。长短本身几乎不参与。

这条实测推翻了"扩展"的方向：**该做的是减词，不是加词**。而它不与
`query-rewrite.md` 矛盾——那次证伪看的是**中位名次**（113→120，去掉壳不改善排序），
这里看的是**阈值通过率**（去掉壳能把 0 条救回 5~6 条）。同一个动作，两个指标。

## 4. 三层，按成本递增

### L0 · 上下文拼接（先做，零延迟零成本）

query = 最近 1~2 条用户输入 + 上一轮回复的**尾部**若干字。

为什么不只加用户输入：`那这个呢` 加上前一句 `那这个呢` 依然没有实体，真正的主题在
上一轮回复里。为什么取尾部：结论、文件名、参数值通常落在最后；这与 1.4.x 里 `clip()`
「头尾各留一半」是同一条经验。

实现位置待定：`agent/pre-step` 的 `messages` 是 `UserMessage[]`、只覆盖当前 step，
拿不到历史 assistant 文本。两条路——
1. 插件端缓存最近一轮的回复（复用 `session/event`），拼进 query；
2. 把 `sessionId` 一并传给服务端，由服务端按会话补最近 N 轮（服务端已有 episode 记录，
   但要确认轮次边界与跨会话污染）。

倾向 1：改动在插件内，不新增服务端语义。

### L1 · 条件触发压缩（需实验）

§3 的实测把这个动作从"补全"改成了"压缩"：把 query 压成 3~6 个名词短语（去掉疑问尾巴、
泛化容器词如「文件/目录/东西」），再与原 query **各检索一次**，按 id 取并为集。

触发条件（任一即可，宁可少触发）：

- 原检索已经弃权——这是最直接的信号，说明措辞没救；
- 含疑问尾巴：`放在哪` `哪个` `怎么配` `是什么` `能不能`；
- 含指代/承接词：`这个` `那个` `它` `上面` `继续` `还是` `改成` `刚才`。

模型选择有硬约束（见 `query-rewrite.md` §1）：**不能用推理模型**，p50 2.6s，
检索路径本身 p50 只有 293 ms；小模型 436~452 ms 是可用上限。且补全只作用于向量路，
BM25 仍走原查询，否则人名/日期/参数值会被稀释。

### L2 · 无条件改写（不做）

已被端到端证伪，不再尝试。

## 5. 验收方式

不用 LoCoMo：它的问句分布与真实对话相反，看不出这个改动的收益。改用**真实会话回放**：

1. 从线上库导出最近若干会话的 episode（含原始 user 文本）；
2. 挑出其中 query 过短的轮次，人工标注「这一轮真正在问什么」；
3. 对比三组查询构造下的命中：原 query / L0 拼接 / L1 补全；
4. 判据用**命中率**，不用相似度分数——`query-rewrite.md` 里已经踩过：分数下降但名次上升。

## 6. 风险

- 拼接引入上一轮的噪声实体，把检索带到无关方向（L0 的主要风险，靠长度上限约束）；
- 每轮多一次模型调用会叠加首字延迟；1.4.x 已经每轮一次摘要/抽取调用，这条路径不能变成两次；
- 会话隔离：补全时绝不能跨租户取上下文。

## 7. 建议顺序

先做 L0，观察一周；只有当 L0 之后仍有大量短 query 走兜底块时，再评估 L1。
